Create the initial framework and working proof of concept for a greenfield product named 'LGR Transformation and Migration'.

PRODUCT CONTEXT

LGR Transformation and Migration is a multi-tenant SaaS platform intended to support Local Government Reorganisation transformation and cloud migration programmes.

The platform will replace migration information currently maintained across multiple Excel workbooks, Azure Migrate exports, assessment reports, application discovery documents, Azure target-build sheets, IP allocation spreadsheets, migration-wave trackers, runbooks and rollback plans.

The product should become the single source of truth for:

- customer and project administration
- discovery and inventory
- application and infrastructure assessment
- migration decisions
- Azure target design
- IP address management
- migration wave planning
- migration readiness
- migration runbooks
- rollback planning
- migration execution tracking
- testing and sign-off
- post-migration reporting

This is Phase 1 / POC. Do not attempt to build every future product feature.

The POC must prove the following primary journey:

Customer
→ Project
→ Application / Server Inventory
→ Migration Decision
→ Azure Target
→ IP Allocation
→ Migration Wave
→ Readiness
→ Runbook

3. ARCHITECTURE PRINCIPLES
--------------------------------------------------

Follow these principles:

- Keep the POC simple.
- Use a modular monolith.
- Do not create microservices.
- Do not introduce Kubernetes.
- Prefer standard framework capabilities.
- Use dependency injection.
- Use async database/API operations.
- Keep domain/business logic outside API endpoint handlers.
- Use DTOs rather than exposing EF entities directly.
- Enable nullable reference types.
- Use clear naming.
- Avoid unnecessary abstractions.
- Do not add paid third-party dependencies.
- Keep the architecture suitable for later Azure deployment.
- Do not leave the repository in a non-building state.

--------------------------------------------------
4. MULTI-TENANCY
--------------------------------------------------

Multi-tenancy is a core architectural requirement.

Every customer-owned business entity must contain CustomerId.

Implement a tenant-aware data-access approach from the start.

For development:
- create a simple TenantContext / CurrentCustomerContext.
- allow a development customer to be selected/configured locally.
- structure it so this can later be populated from Microsoft Entra ID claims.

API requests must not accidentally return records from another customer.

Document the multi-tenancy architecture.

IMPORTANT:

Do not use hostname as the database primary key.

Use immutable Guid IDs for database primary keys.

For Server enforce the business uniqueness rule:

CustomerId + Hostname = unique
